# Postgres tuning & partitioning — recovery notes

On 2026-08-17 the `pgprojeto` container was recreated and every optimization that lived only
inside the Postgres data volume was lost: 9 `ALTER SYSTEM` GUC settings and 5 tables that had
been converted to native partitioning. Nothing here was persisted anywhere versioned — it only
existed as live state in that one volume. This folder is the fix: the GUC settings now live in
`postgres/docker-compose.yml` + `configs/secrets.env` (survive `make clean`), and the
partitioning migrations are saved here so they can be re-run any time a fresh/empty database
needs them again.

## GUC tuning (now in `postgres/docker-compose.yml` `command:` + `configs/secrets.env`)

13 GUCs total: the 10 below (memory and WAL, 2026-08-09) plus 3 I/O settings added later
(2026-08-21, see "I/O tuning" section below). `PG_SHARED_BUFFERS` is `1536MB` today, raised
from the original `1GB` alongside the I/O changes to keep the "25% of `mem_limit`" ratio after
`mem_limit` itself went from `4g` to `6g`.

Originally diagnosed and applied 2026-08-09 while investigating erratic seeder throughput
(batches alternating between 20-30s and 5-10min). Root cause: `person.customer`'s indexes alone
exceeded the default 128MB `shared_buffers`, forcing every INSERT to fall back to disk reads
(`pg_stat_activity` showed `wait_event=DataFileRead` stalls of ~2min) — worse on WSL2, where
disk I/O is virtualized through an extra Windows layer.

| Var | Value | Why |
|---|---|---|
| `PG_SHARED_BUFFERS` | 1536MB (was 1GB) | Was already the first fix (2026-08-12) and already survived, kept for reference. Raised to 1536MB on 2026-08-21 to stay at roughly 25% of `mem_limit` after `mem_limit` went from 4GB to 6GB (see "Container memory and shared memory" below). |
| `PG_WORK_MEM` | 128MB | Per-sort/hash-join memory, raised from the 4MB default for the JSONB/GIN-heavy queries this schema uses. |
| `PG_MAINTENANCE_WORK_MEM` | 1GB | Speeds up index builds/VACUUM on the large fact tables. |
| `PG_EFFECTIVE_CACHE_SIZE` | 4GB | Planner hint matching the container's actual available cache (mem_limit), not the 4GB Postgres default assumption. |
| `PG_MAX_WAL_SIZE` | 16GB | Fewer checkpoints under sustained bulk-insert load — checkpoints cost expensive random I/O bursts on the WSL2 virtualized disk. Raised in two steps (4GB → 16GB) as the seeder volume grew. |
| `PG_CHECKPOINT_COMPLETION_TARGET` | 0.9 | Spreads checkpoint I/O over more of the checkpoint interval instead of bursting. |
| `PG_WAL_COMPRESSION` | on | Trades idle CPU for fewer WAL bytes written. |
| `PG_SYNCHRONOUS_COMMIT` | off | Commits stop waiting on WAL fsync. **Risk accepted explicitly by the user on 2026-08-09**: on a real crash (not just a container restart) the last few commits could be lost — acceptable because this is 100% synthetic, regenerable-by-reseeding data, never production. |
| `PG_FSYNC` | off | Removes disk sync entirely, not just at commit — the most aggressive lever Postgres exposes. **Risk accepted explicitly by the user on 2026-08-09** after being warned this crosses into "could corrupt a data page on an OS/hardware crash, not just lose recent transactions" — Postgres's own docs say only do this if you can recreate the cluster from scratch, which is true here. |
| `PG_FULL_PAGE_WRITES` | off | Same explicit approval as `PG_FSYNC` above, same risk class. |

**Do not carry `PG_FSYNC=off` / `PG_FULL_PAGE_WRITES=off` / `PG_SYNCHRONOUS_COMMIT=off` into any
environment with real, non-regenerable data.** They're safe here only because every table in
this stack is seeded synthetic data that can be regenerated by re-running the DAG.

All 13 settings are `sighup`-context (Postgres can pick them up on a config reload/container
restart, no need to reinitialize the data directory) — see the `command:` block in
`postgres/docker-compose.yml`. If you ever need to change one, edit `configs/secrets.env` and
run `docker compose -f postgres/docker-compose.yml up -d` (recreates the container, keeps the
volume).

## I/O tuning (added 2026-08-21)

Found while chasing task timeouts under concurrent load in `nexomart_seeder_dag`: Postgres was
still on its HDD-era I/O defaults, even though the volume is SSD/VM-backed storage.

| Var | Value | Why |
|---|---|---|
| `PG_EFFECTIVE_IO_CONCURRENCY` | 200 (was 1) | Lets Postgres issue many concurrent read requests per query, matching what SSD-backed storage can actually do in parallel. |
| `PG_MAINTENANCE_IO_CONCURRENCY` | 200 (was 10) | Same idea, for maintenance operations (VACUUM, index builds). |
| `PG_RANDOM_PAGE_COST` | 1.1 (was 4) | Tells the query planner random reads are nearly as cheap as sequential ones, true for SSD/VM storage, false for spinning disks (the Postgres default assumes an HDD). |

A sequential write benchmark (`dd`) measured a healthy 187MB/s, confirming the disk itself was
not the bottleneck, this was purely under-tuned settings plus real concurrency from several
heavy tasks landing in the same scheduling window. See `docs/SEEDER_MICROBATCHING.md`'s
"Problem 6" for the full investigation, including why `dagrun_timeout` was removed rather than
tuned (a timed-out task's client process is killed, but the in-flight Postgres query keeps
running and competing for I/O regardless).

## Container memory and shared memory

`shm_size` (Docker's `/dev/shm` allocation) defaults to 64MB and was never set explicitly for
`pgprojeto`. `maintenance_work_mem=1GB` (see GUC table above) needs a shared-memory segment far
bigger than that for `VACUUM`/`ANALYZE`, so every attempt failed silently with `could not resize
shared memory segment ... No space left on device`, autovacuum included. This is why several
tables had `last_analyze`/`last_autoanalyze` stuck at `NULL` and wildly wrong row-count
estimates in `pg_stat_user_tables` for weeks, ANALYZE had never actually completed on them.

Fix: `postgres/docker-compose.yml` sets `shm_size: 2gb` and raised `mem_limit` from `4g` to
`6g` (to keep headroom for `work_mem` per connection on top of `shared_buffers` + `shm_size`).
Both require a full container recreate, not just a restart, since they are set at
container-creation time. Recreating `pgprojeto` can crash `airflow_scheduler`'s DB connection
hard enough to require a manual `docker start airflow_scheduler`, check the scheduler's
container status after any `pgprojeto` recreate.

Full writeup: `docs/SEEDER_MICROBATCHING.md`, "Problem 5".

## Data volume

`pgprojeto` bind-mounts `${POSTGRES_DATA_DIR}` (`/mnt/wsl/postgres-ssd/pgdata`, `configs/secrets.env`) into
`/var/lib/postgresql/data`. That path is a dedicated disk, `L:\WSLDisks\postgres-data.vhdx`, attached to WSL2 by
the scheduled task `MountPostgresSSD-WSL` (`scripts/windows/mount-postgres-ssd.ps1`, logon + every 5 min; register it with `setup-postgres-mount-task.ps1`). If the disk is
not mounted, Docker would create an empty directory and Postgres would initialise a brand-new empty cluster, so
`make up`, `make up-postgres` and `make start` stop first (`make check-postgres-disk`).

History: the cluster (`nexomarket_db`, `airflowdb`, `metastore`, ...) briefly lived in a `pgprojeto_data` named
volume inside the Docker Desktop vhdx. When that vhdx was lost (failing `F:` drive, 2026-10-01), the cluster was
restored by pointing the container back at this disk (last clean shutdown 2026-09-28).

## `AuditMixin.created_at` index was never actually attached to any table

`configs/api/base.py`'s `AuditMixin` declared its `created_at` index via `@declared_attr` with a
string column reference, which only resolves through `__table_args__`, and every real model
overrides `__table_args__` for schema-qualification, silently dropping the index declaration.
Confirmed live: no `ix_*_created_at` index existed on any table, including ones untouched by the
partitioning migrations. Fixed by declaring the index with `index=True` directly on the
`Column(...)` instead. Existing databases still need the retrofit migrations in this folder
(`001`-`006`) to get the index; only fresh databases pick it up automatically from the model now.

## `person.customer_br` index corruption (2026-08-21)

A live seeder run failed with `IndexCorruptedError: right sibling's left-link doesn't match`
against `customer_br_row_guid_country_id_key`. Most likely cause: `fsync=off` +
`full_page_writes=off` (both accepted risks above, safe only for this synthetic-data
environment) combined with an earlier hard-killed task leaving a B-tree page inconsistent.
Fix: `REINDEX TABLE person.customer_br;`, no schema change. If a similar corruption error shows
up on another table, the same command is the fix, confirm the repair actually worked via
`pg_index.indisvalid`, Airflow's automatic retry can appear to succeed without the corruption
actually being gone.

## Partitioning migrations (`migrations/00*.sql`)

Originally applied 2026-08-13 as part of chasing the same root cause further: even with
`shared_buffers=1GB`, the indexes on the biggest fact/dimension tables kept outgrowing it as
seeded volume grew (measured at the time: 7 relations = 97.4% of `shared_buffers`, dominated by
`person.customer` and `sales.salesorder`'s two JSONB GIN indexes). Raising `shared_buffers`
further only postpones the problem; partitioning the largest tables by their natural time/geo
key keeps each partition's working set small enough to stay cache-resident.

| Table | Partition strategy | Key |
|---|---|---|
| `person.customer` | LIST | `country_id` (one partition per country, `customer_other` DEFAULT catch-all) |
| `sales.salesorder` | RANGE | `order_date`, monthly |
| `warehouse.transactionhistory` | RANGE | `transaction_date`, monthly |
| `purchasing.purchaseorderheader` | RANGE | `order_date`, monthly |
| `marketing.dailyperformance` | RANGE | `date_ref`, monthly |

Every partitioned table's primary key had to become composite (id + partition key), which is a
Postgres requirement for partitioned tables. That broke the single-column foreign keys that
other tables held into these five — those FKs are **not** recreated; the relationship is now
enforced by the seeders only (each seeder always fetches real, live IDs before inserting; see
the corresponding comments in the affected model files under `dbapi/api/models/`). This was a
deliberate tradeoff made and committed back on 2026-08-13, not something lost by the
2026-08-17 incident — only the DB-level partitioning DDL itself was volume-local and lost.

### Re-running a migration

Each script in `migrations/` is written as `RENAME old table → INSERT ... SELECT into new
partitioned table → DROP old`, so it's safe to run whether the target table currently has data
(a real recovery, like 2026-08-17) or is completely empty (a fresh `make clean && make up`
before any seeding has happened — the `INSERT ... SELECT` just copies zero rows). Run them in
numeric order against `nexomarket_db` (includes `006`, independent index-only migration for the
fan-out seeders' FK lookups — not partitioning, but lives here as the same numbered set):

```bash
for f in configs/postgresql/migrations/00{1,2,3,4,5,6}_*.sql; do
  docker exec -i pgprojeto psql -U admin -d nexomarket_db -v ON_ERROR_STOP=1 < "$f"
done
```

Re-applied live 2026-09-03 after the 2026-08-17 loss went undetected for a while — this time
against tables that already had millions of real rows (`salesorder` 12.6M/17GB,
`dailyperformance` 18.7M/15GB), not the empty tables the first application ran against. Row
counts verified identical before/after for all 5 tables, zero rows landed in any `_other`/
`DEFAULT` partition. Took 88-532s per table (`INSERT ... SELECT` copying the existing rows into
the new partitioned layout) — budget for that on a populated database, it's not instant like it
was against an empty one.

Partition bounds are hardcoded to specific months (see each seeder's lookback window in the
comments inside each script) — if the seeders' date ranges drift far enough in the future, the
`_other`/`DEFAULT` partition will silently absorb everything outside the declared bounds
instead of failing. Not urgent, but worth widening the bounds (or switching to `pg_partman` for
automatic partition management) if this project runs long enough for that to matter.

## `salesordernumber` had no index (found and fixed 2026-09-03)

`sales.salesorder`'s dedup helper (`generate_unique_business_ids` in
`dbapi/api/utils/cli_common.py`, shared by the sales/purchasing/warehouse/returns seeders)
checks uniqueness with `SELECT ... WHERE <business-key column> IN (...)`. For
`purchaseorderheader`/`transactionhistory`/`returnorder` that column *is* the primary key, so
it's already indexed. `salesorder` is the one table where the business key
(`salesordernumber`) is a separate column from the surrogate PK (`salesorder_id`) — and nothing
indexed it. `EXPLAIN ANALYZE` on a 3-value `IN (...)` lookup: **8,485ms**, full parallel seq
scan over ~11.6M rows. Migration `002_partition_salesorder.sql` already declares `UNIQUE
(salesordernumber, order_date)` on the partitioned table, so re-running the partitioning
migration fixed this as a side effect — no separate index migration needed. Re-verified with the
same query post-migration: **28.8ms** (~295x), via per-partition `Bitmap Index Scan`/`Index Only
Scan` instead of a seq scan.

## `COALESCE(updated_at, created_at)` expression indexes (2026-09-04)

`dbapi/api/seeder/ingestions/ingestion_common.py`'s incremental extraction (see
`docs/INGESTION_INCREMENTAL.md`) filters every table with
`WHERE COALESCE(updated_at, created_at) > :watermark`. A plain btree index on `created_at`
(every table already has one) can't be used for that — wrapping a column in `COALESCE(...)`
isn't sargable against an index built on the bare column, confirmed with `EXPLAIN`: still a Seq
Scan per partition even with `created_at` indexed. Added a matching expression index on each of
the 5 partitioned tables:

```sql
CREATE INDEX <table>_coalesce_idx ON <schema>.<table> (COALESCE(updated_at, created_at));
```

**`CREATE INDEX CONCURRENTLY` does not work directly on a partitioned table** (`ERROR: cannot
create index on partitioned table "..." concurrently`, still true as of Postgres 16) — the
non-blocking build has to happen per-partition, then get attached to an umbrella index on the
parent:

```sql
-- once per partition (non-blocking, safe with the seeder writing concurrently)
CREATE INDEX CONCURRENTLY IF NOT EXISTS <partition>_coalesce_idx
  ON <schema>.<partition> (COALESCE(updated_at, created_at));

-- once per table, after all its partitions' indexes above exist
CREATE INDEX IF NOT EXISTS <table>_coalesce_idx ON ONLY <schema>.<table>
  (COALESCE(updated_at, created_at));

-- once per partition, links it into the umbrella index (only valid once every partition is attached)
ALTER INDEX <schema>.<table>_coalesce_idx ATTACH PARTITION <schema>.<partition>_coalesce_idx;
```

A first attempt at plain `CREATE INDEX CONCURRENTLY` directly against the parent tables hung for
28+ minutes waiting on a `virtualxid` lock — with the 15-minute seeder DAG and ingestion both
writing, there's rarely a fully idle moment for `CONCURRENTLY`'s snapshot to wait out. The
per-partition build above doesn't have that problem (each partition's own build only waits on
that partition's writers, and killing the seeder/ingestion DAG runs briefly cleared it besides).

## History partitions and future months (`migrations/007a_*.sql`, `007b_*.sql`, applied 2026-10-01)

The monthly bounds only covered a few recent months, so everything older sat in each table's `*_other` DEFAULT
partition (`sales.salesorder_other` held ~60M rows / 78 GB, 2020-01 to 2026-05) with no partition pruning, and
anything past the last bound would have landed there too. Nothing creates monthly partitions automatically.

- `purchaseorderheader` and `salesorder`: the old DEFAULT was detached and re-attached as `<table>_history`
  (`FROM (MINVALUE) TO (<first monthly bound>)`), zero-copy, after a validated CHECK let ATTACH skip the scan.
  A copy into yearly partitions would have needed ~156 GB on a disk with ~131 GB free.
- `transactionhistory` and `dailyperformance`: the DEFAULT mixed old history with rows past the last bound, so it was
  split by `INSERT ... SELECT` in one transaction (small tables, row counts checked before the DROP).
- All four now have monthly partitions through 2027-12 and an empty DEFAULT. **Create the next months before
  2028-01** (rerun the loop in the migration) or rows fall back into `*_other`.
- `person.customer` is LIST by country and was not touched (its DEFAULT has ~78k rows).
- The landing layer in MinIO is unaffected: it partitions by event date and ignores Postgres partitions
  (`list_schema_tables()` filters `NOT relispartition`).
