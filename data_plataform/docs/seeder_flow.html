A batch's path to the database

Each dot is a row of data. A run starts in Airflow and passes the contract gate; the rows are then generated, validated and deliberately dirtied before going to Postgres. Rows that Pydantic rejects go to the quarantine bucket.

With 2 rejected rows out of 100, the rate goes over 1% and the task fails.

What happens, in order

  1. Airflow triggers nexomart_seeder_dag every 15 minutes.
  2. contract_drift_check compares the YAML contract, the Pydantic schema and the table. If they diverge, the run stops here.
  3. The seeder generates rows from samples/ and Faker, using real foreign keys from the database.
  4. Pydantic validates each row. A rejected row goes to quarantine and the valid ones continue.
  5. Chaos deliberately dirties 5% to 10% of the rows that were already validated.
  6. The physical check sends rows the table would refuse to quarantine (NULL in a NOT NULL column, text longer than the column, number overflow). Then q.finish() checks the rate: above 1% the task fails before touching the database.
  7. bulk_copy, from utils/cli_common.py, sends the whole batch with COPY.
  8. Postgres receives the rows, including the deliberately dirty ones.

Simulation: 100 rows per run and 8% chaos to keep it readable. In the real seeder each run has 1,000 to 50,000 rows. The 1% limit is checked from 50 rows on and again at the end, and validation, chaos and the send happen on the batch, not row by row.
